# マシュマロのURL取り込みを再調査した結果

調査日: 2026-10-11（日本時間）。対象: [Issue #8](https://github.com/hekiruligames/jp-letters-lua/issues/8)。

## 結論

**公開された個別のお便りは、確認した2件ではURLから本文を取得できた。** 通常のHTTPS接続で公開ページを読み、HTMLから質問本文を抽出した。10月9日にこの環境で発生した403は、今回の接続では再現しなかった。

ただし、これで「受信箱の未公開のお便りをURLだけで取り込める」「自動取得を公式に認められている」と確認できたわけではない。公式の取得API・外部ツール向けの連携条件は、調べた範囲では見つからなかった。

配信前の準備を楽にする目的では、**自分の受信箱を手動でコピーし、貼り付けた内容からお便りを選んで一括登録する方式**を先に検討する。公開URLの単件取得は別の候補として残す。

この調査では製品の機能を変更していない。運営への問い合わせも送信していない。

## URLによってできることが違う

| 入力するもの | わかったこと | jp-lettersでの扱いの候補 |
| --- | --- | --- |
| 募集ページのURL `https://marshmallow-qa.com/[ユーザーID]` | お便りを送るページ。個々の受信本文は指定できない | 募集URLだけで受信箱を取り込むことはできない |
| 公開済みの個別URL `/messages/[ID]` | 公開サンプル2件では、ログインなしでHTMLの本文を取得できた | 利用者が指定した自分宛ての1件を取得し、登録前に確認する |
| ログイン中の受信箱 | 本人の認証が必要。今回はアクセス・取得を検証していない | 本人が表示した本文のコピー・TXT取り込みを使う |
| 「こっそり回答」のURL | 公式ヘルプは、URLを公開すると送信者以外にも見えると説明している | URLだけで公開の意図や取得権限を判定できない。自動収集の対象にしない |

URLの違いの根拠: [募集URLの公式説明](https://help.marshmallow-qa.com/メッセージ募集のURLを短くしたい-66c7eb0f8a764f001da3ee1b)、[こっそり回答の公式説明](https://help.marshmallow-qa.com/こっそり回答-66c7eb108243f1001d67239a)。ログイン不要で閲覧できることと、本文を再利用する権利があることも別の確認になる。

## 公式資料から確認できた範囲

- [公式ヘルプ](https://help.marshmallow-qa.com/受け取ったメッセージの使い方に制限はありますか？-66c7eb103f79db001cc49873)は、受信したメッセージの利用に制限はなく、受信者が知的財産権を持つと説明している。[基本利用規約](https://marshmallow-qa.com/terms/service)にも受信者の権利と自由な利用の説明がある。自分が受け取った本文のコピー・貼り付け・配信利用には、この説明が根拠となる。
- [包括的な利用規約](https://marshmallow-qa.com/terms/paid_service)第7条では、過度な負荷、運営妨害、不正アクセス、他利用者の情報収集などを禁止している。第9条は本文とサービス自体の権利を区別している。本文の利用許諾から自動アクセスの許諾まで導くことはできない。
- 規約・公式ヘルプ・公式サイトを「API」「開発者」「エクスポート」などで確認した範囲では、第三者向けのメッセージ取得API、認証方法、取得頻度の公式文書は見つからなかった。APIが存在しないという断定ではない。検索結果に出る「APIについてのお便り」も、サービスのAPI文書とは区別した。
- 確認した規約では、スクレイピングという語による一律の禁止も、今回の単件取得を明示的に許諾する説明も確認できなかった。運営による個別の許諾は未確認。

`robots.txt` の当日の内容は次のとおりだった。

```text
User-agent: *
Disallow: /apt/

User-agent: Twitterbot
Allow: /apt/
```

[robots.txt](https://marshmallow-qa.com/robots.txt)では、一般クローラーに対して `/messages/` を除外する指定はなかった。これはクローラー向けの指定で、API契約や利用規約上の許諾に置き換わるものではない。`/apt/` は取得していない。

## 公開ページで実際に確認したこと

検索結果に掲載された公開のお便り2件に、Cookie・アカウント情報なしで通常のHTTPS GETを行った。画像、非公開API、ログイン後のページは取得していない。本文や取得したHTMLはリポジトリ・配布物に保存せず、以下の技術的な結果だけを記録する。

| 確認項目 | [公開サンプルA](https://marshmallow-qa.com/messages/64ec862b-8a62-48f5-997f-b3ced93032c2?hl=ja) | [公開サンプルB](https://marshmallow-qa.com/messages/3441846c-2f8e-4994-93c2-481072eacf8f) |
| --- | --- | --- |
| HTTPステータス | 200 | 200 |
| HTMLの大きさ | 87,560 bytes | 91,792 bytes |
| HTML内の質問本文 | 77文字・1行 | 446文字・8行 |
| 本文の所在 | `.message-card__text` | `.message-card__text` |
| `og:title` | 本文とサイト名を含む | 本文とサイト名を含む |
| `description` | 質問本文と異なる | 質問本文と異なる |
| `og:description` | なし | なし |

HTMLを解析して質問の要素から文字列を取り出し、`br` を改行に変換した。2件では、本文と `og:title` からサイト名を除いた文字列が一致した。**`description` を質問として取り込む実装は不適切**で、回答の説明を取り込んでしまう。

当日のHTMLには、ブラウザでJavaScriptを動かす前から本文が含まれていた。そのため、この2件の取得には画像の文字認識やブラウザの自動操作は必要なかった。HTML中に別の取得先らしい属性もあったが、公式APIと判断せず、アクセスしていない。

`Origin: http://127.0.0.1:17760` を指定してサンプルAをもう1回取得しても200だったが、`Access-Control-Allow-Origin` はなかった。今回の応答では、通常のブラウザのクロスオリジン取得で本文を読めない。

検証は公開2件に限る。非常に長い本文、伏字、絵文字、削除済みURL、公開していないお便り、閲覧条件が違うページ、利用者のMac・Windowsでの取得は未検証。HTMLの要素名は公式APIではなく、サイトの変更で壊れる可能性がある。

## 現行のLua版に追加する場合の技術的な課題

現行の操作画面は `http://127.0.0.1` 上で動く。CORSに加え、[ローカルサーバーのCSP](../letters/runtime/http.lua)も接続先を自分自身に限定している。ブラウザの `fetch` にURLを渡すだけでは対応できない。

Lua側から取得すればブラウザのCORSを解決できるが、現在のHTTPモジュールはローカル接続を受けるサーバーで、外部へ接続するHTTPSクライアントではない。Windows・macOSで動くHTTPS取得、証明書検証、タイムアウト、OBSを止めない非同期処理を別途実装・検証する必要がある。Lua版でも原理上は可能だが、既存機能だけで完成する変更ではない。

URL取り込みを試作するなら、次の範囲にする。

- 本人が指定した自分宛ての公開個別URLを、ボタンを押したときに1件取得する。募集URLは区別して案内する。
- HTTPSの正規ドメインと個別ページの形式だけを受け付ける。リダイレクト先も確認し、任意のURLを取得できる機能にしない。
- 時間・取得量を制限し、取得した本文をプレビューしてから一覧に登録する。サービス側のHTMLをそのまま表示しない。
- エラーや本文を見つけられない場合は、手動の貼り付けへ案内する。ログイン情報を要求せず、常時巡回や自動再試行は行わない。

これは設計候補であり、実装・運営の許諾確認が済んだ仕様ではない。

## 既存のツールで見つかった3つの方式

以下は公開されている説明を読んだ結果。第三者の製品をインストール・購入したり、そのコードを流用したりしていない。存在することだけで、マシュマロ運営の許諾や現在の動作を確認できるわけではない。

| ツール | 公開説明にある方式 | 参考になる点と限界 |
| --- | --- | --- |
| [ましゅびん](https://booth.pm/ja/items/8782886) | 公開された個別URLから、アカウント情報を入力せず質問を取得 | 公開URLだけを扱う製品の実例。作者も取得失敗・仕様変更の可能性を明記している。実装方式は未確認 |
| [サクラミ＠素材屋の質問表示ツール](https://booth.pm/ja/items/8192906) | 受信箱を全選択してコピーし、貼り付けた内容から質問を抽出 | 手動コピーからの一括登録の実例。ただし商品説明では、この一括追加機能はWindows専用とされる。Mac/Safariでの裏付けには使えない |
| [OBSマシュマロもぐもぐマシーン](https://lab.horaiken.jp/marshmallow/)／[原稿製造機](https://chromewebstore.google.com/detail/kdnknenhndmipooeoocnccnpibjdgpjl) | Chrome拡張を押して、表示中の未読のお便りをTXTに書き出す。追加分は本人が「もっとみる」で表示する | 本人が開いた画面からローカルファイルを作る方式。Chrome専用で、Safari用ではない。拡張本体の処理や権限は監査していない |

もぐもぐマシーンの説明は、TXT内のお便りを「改行3回、`///`、改行3回」で区切るとしている。jp-lettersの[既存のTXT取り込み](../letters/web/core.js)はこの区切りを扱える。自作の2件の短い本文を使い、LF・CRLF両方で2件に分かれることを実際の `importText` 関数で確認した。拡張が出力した実ファイルやその現在の動作までは未検証。

Chromeウェブストアには原稿製造機1.0.1・2024-09-01更新と掲載されていた。データを収集しないという表示は作者の申告であり、この調査で安全性を検証した結果ではない。

## 次に取り組むなら

1. **コピーした受信箱からの一括登録を検討する。** 今の本文貼り付け・TXT・JSONを維持し、Mac/SafariとWindowsで本人がコピーしたサンプルを確認する。管理画面の文言が混じる場合は取り込み前に候補を並べ、利用者が選択・修正してから保存する。jp-letters自身はマシュマロにアクセスしない方式にする。
2. **表示中の本文を書き出す補助機能を別案として確認する。** ブックマークレットや拡張で画面の本文だけを取り出す方式は、文字列だけからの判別より正確にできる可能性がある。追加の取得通信や受信箱の自動巡回を伴わない設計に絞り、許容される条件とSafari対応を調べる。
3. **公開URLの単件取得は、公式連携条件を確認したうえで試作する。** 公開2件の取得成功は技術的な前進。ただし配信前の未公開のお便りにも役立つかは別途検証が必要で、これだけを先に実装しても準備の手間が十分に減るとは限らない。

Issue #8は、公式連携条件と未公開のお便りの扱いを確認するため、開いたままにする。

### コピー方式の試作（同日追記）

利用者の受信箱と個別カードの画像、およびSafariの「受信箱 → もらったメッセージ → 未確認」からコピーした実テキスト2件を確認した。一覧には本文・相対日時・「画像ダウンロード／確認済みにする」の操作欄のほか、運営のお知らせとナビゲーションが含まれる。

0.4.0に、貼り付けから候補を作り、確認・編集・選択してOBSへ保存する機能を追加した。公開ページのクラス名が通常のコピーに必ず残るとは限らないことも確認し、実テキストの日時・操作欄からの判別を優先した。自動の取得通信を伴わない。[使い方と検証範囲](validation-v0.4.0.md)。Mac・WindowsのOBS実機とSafari上の操作画面は別途確認する。
